# 02 Swift 代码约定

[返回主 PRD](../PRD.md) · [架构](01-project-foundation.md) · [验收](10-delivery-and-acceptance.md)

本文件约束后续原生实现，不要求本次生成 Swift 文件。旧 Flutter 的语言、目录及工具规范不直接用于原生项目。

## 1. 命名与组织

- 类型、协议使用 UpperCamelCase，方法与属性使用 lowerCamelCase；名称表达业务含义，避免 `data1`、`tempModel` 等泛化命名。
- 文件按主要类型或职责命名；业务模块边界与 01 保持一致。视图结构过长时拆成有含义的子视图，不用一个 View 包含所有页面。
- 限制访问级别，默认不暴露可变状态；不为所有实体引入继承或无实际用途的协议。
- 界面文案集中于可本地化资源；API 字段和枚举原值必须与后端一致。

## 2. 类型与数据

- DTO 使用明确 Codable 类型，金额字段为 String；业务层转换为精确金额类型，不能使用 `[String: Any]` 贯穿全项目。
- 业务 ID 使用可覆盖后端安全整数范围的整数类型；提交 ID 来自真实服务，不生成本地业务 ID。
- `occurredDate`、月份、年份建模为自然日期 / 周期，不套用统一 ISO 时间点解码。
- 可空字段明确建模；写入 `title` / `remark` 清空时须显式 encode null，不能因 `encodeIfPresent` 自动省略而违背完整 PATCH 契约。
- 成功无 data 与需要 data 的查询使用不同解码路径。坏响应不得用空模型兜底后显示成功。
- 对非法输入和未知枚举给出可诊断错误，不在正式流程用 `try!`、强制解包或 `fatalError` 掩盖可恢复问题。

## 3. 并发与生命周期

- UI 状态在 MainActor 上修改；网络等待不阻塞主线程。长期凭证、刷新和身份切换通过 actor / 串行操作协调。
- 明确 Task 的持有者、取消时机、结果接收条件；View 重算不重复启动写入或创建会话。
- 对跨 actor 数据遵守所选 Swift 模式的 Sendable 检查，不用普遍 `@unchecked Sendable` 规避问题。
- 刷新任务共享、请求最多一次认证重放；JSON body 可复用。传输重试与认证重放不使用同一个无限循环。
- 相同提交动作有加载锁，关闭、取消、保存和子面板返回分别处理；不可通过手势绕过未保存确认。

## 4. 注释与文档（强制要求）

所有方法、变量都必须写中文注释，所有代码在关键节点也必须写中文注释，方便理解。本要求适用于所有模块的自有代码，包括后续 AI 生成或人工编写的源码、测试、SwiftUI Preview 和辅助脚本；不得以“AI 生成”“方法简单”“变量局部”或“命名已经清楚”为由省略。

### COMMENT-01：所有方法必须有注释

- 覆盖所有函数、方法、初始化器、协议方法、计算属性的 getter / setter，以及事件处理、异步任务和回调闭包的处理逻辑，不限访问级别或代码长度。
- Swift 具名方法 / 函数使用 `///` 文档注释，说明用途、每个参数的含义、返回结果；有异常、状态修改或其他副作用时说明对应行为。其他语言的辅助脚本使用对应语言的注释格式。
- 闭包在定义处或执行逻辑前写说明，解释触发时机、输入参数及处理目的；不能因方法没有名称而跳过。
- 注释需要体现业务约束，例如金额单位、自然日期格式、归档条件、会话状态与调用前提，不能只有“执行处理”等空泛文字。

### COMMENT-02：所有变量必须有注释

- 覆盖所有 `var` / `let`、常量、类型属性、实例属性、模型字段、局部变量、循环变量、条件绑定变量、解构绑定、闭包参数与方法参数；SwiftUI 的状态、绑定、环境属性及 `body` 等计算属性同样适用。
- 变量 / 属性在声明前写中文说明；同一行声明多个变量时，每个变量的含义都必须可辨认。参数可在方法文档的参数项或闭包说明中逐个解释，不要求在签名中重复同一说明。
- 说明变量保存什么、用于什么；涉及状态时写清作用域、持有者和生命周期，涉及金额 / 日期 / Cookie 时写清单位、格式或安全边界。
- 临时变量、循环索引和测试数据也不能省略。应说明其在当前处理中的意义，不使用“变量 i”“临时值”这类无助于理解的注释。

### COMMENT-03：所有代码的关键节点必须有注释

- 在关键步骤、业务判断、重要分支、循环处理、异常处理、异步状态切换和跨模块副作用发生处添加中文行内 / 分段注释，说明“为什么这样处理”“依据什么规则”“如何处理边界”。
- 必须覆盖但不限于：刷新共享与轮换、身份代次校验、Keychain 原子替换、金额解析和精度保护、日期桥接、查询白名单、标签草稿事务、归档口径、旧响应拦截、表单返回保护，以及写成功与刷新失败的区分。
- 方法级注释、变量注释和关键节点注释必须同时具备，不能互相替代；不能仅在文件顶部概述后省略具体代码处的说明。

类型与协议同样提供中文用途说明。修改代码时同步更新对应注释，避免注释与实际行为不一致。检查既要覆盖是否遗漏，也要人工核对说明是否准确、能否帮助理解，不以注释数量替代质量验收。

## 5. 原生资源与界面

- 视觉数值集中在 DesignSystem，使用 08 的语义 Token；禁止页面各自选一套黄色或收支配色。
- 分类图标映射集中维护；未知 key 有占位。运行时不依赖 Web Symbol、CSS 或远程图标脚本。
- Preview 可使用明确标记的 fixture，正式依赖装配不能落回假接口；测试账号和凭证不提交到仓库。
- 支持 Dynamic Type、VoiceOver、Reduce Motion；不通过全局锁字号或隐藏错误来通过布局检查。

## 6. 检查要求

后续工程至少完成编译、关键契约 / 会话测试、关键页面 UI 验证，以及 COMMENT-01–03 的全覆盖注释检查；所有方法、变量和关键节点的注释缺失均须补齐。可使用检查工具辅助发现遗漏，但必须人工复核参数、闭包、局部变量、关键分支及注释准确性。格式 / lint 工具是否引入由工程初始化记录确定，不将未安装工具写成已经通过的检查。具体测试范围与设备场景见 [10](10-delivery-and-acceptance.md)。
