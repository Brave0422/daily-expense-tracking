# 03 账户与认证

## 1. 页面与流程（AUTH-01）

| 页面 | 输入与操作 | 成功结果 |
| --- | --- | --- |
| 启动恢复 | 品牌图形、恢复状态；临时失败可重试 | 恢复成功进流水，无凭证进登录 |
| 登录 | 邮箱、密码、显示密码、登录；注册 / 忘记密码入口 | 建立可恢复会话，进入流水 |
| 注册 | 邮箱、密码、六位验证码、发送验证码 | 注册成功后用同一输入登录 |
| 忘记密码 | 邮箱、新密码、六位验证码 | 提示重置成功，返回登录，不自动登录 |
| 修改密码 | 新密码、六位验证码；不输入另一邮箱 | 提示成功，清空敏感字段，返回账户安全 |

认证页采用浅灰背景、白色表单卡、黄色主按钮和“账”品牌标识；按钮使用深色文字。输入框单列排列，有字段标签，不仅依赖 placeholder。密码显示切换保持焦点，邮箱键盘关闭自动首字母大写，验证码允许系统自动填充。

邮箱 trim 并转小写；密码 6–20 字符且不 trim，不增加后端未要求的复杂度；验证码六位数字字符串，保留前导零。字段校验失败就近提示；提交时禁用重复操作并聚焦首个错误。字符长度规则见 09。

注册成功但自动登录失败时提示“注册成功，请登录”，保留邮箱并回登录流程，不重新提交注册。普通失败保留当前输入；成功、用户明确放弃或会话销毁时清理密码 / 验证码。不长期保存密码。

## 2. 会话状态（AUTH-02）

状态至少包括：恢复中、未登录、已登录、恢复暂时失败、退出处理中、本地凭证处理失败。恢复完成前不闪现业务或登录页。

1. 初始化当前 API 环境的 CredentialStore，读取并校验 Cookie 快照。
2. 无凭证 / 已到期：清理该环境失效数据，进入登录，不发送无意义的 refresh。
3. 有可用 Cookie：请求 `POST /auth/refresh`，校验 Access Token 和轮换 Cookie，安全保存完成后进入已登录。
4. 刷新明确返回 401：统一清理当前身份并进入登录。
5. 超时、断网、5xx：保留凭证，进入“暂时无法恢复，重试”；不把网络故障当作密码错误或主动退出。
6. Keychain 暂不可读 / 写失败与“没有凭证”区分；显示可重试错误，不静默创建空身份。

当前没有 `/users/me` 或资料查询接口。当前登录输入的邮箱可以在本次会话展示；仅通过 Cookie 恢复且没有可信邮箱时，管理页显示“已登录”，不伪造邮箱。此版不要求解析 JWT 作为用户资料来源。

## 3. URLSession 与 Keychain（AUTH-03）

后端登录 / 刷新在 JSON 中只返回 `{accessToken}`，Refresh Token 来自 `Set-Cookie` 的 `refresh_token`。沿用服务端 `/auth` Path、HttpOnly、SameSite=Lax、到期时间，生产 Cookie 为 Secure。

原生实现约束：

- Access Token 只在当前进程内存，受保护请求发送 `Authorization: Bearer ...`。
- 使用 ephemeral URLSession，关闭系统自动 Cookie 接收 / 发送并禁用默认持久 Cookie Store；由统一适配层受控解析和构造 Cookie，避免系统层在身份检查前自动回写迟到响应。
- 利用 Foundation Cookie 解析能力处理 Set-Cookie，不按逗号粗暴拆分，因为 Expires 本身含逗号；处理多个头值、替换和删除语义。
- Keychain 保存完整 Cookie 属性快照，包括名称、值、主机 / domain、host-only 范围、path、expires / max-age 推导的到期、Secure、HttpOnly 等。不能只保存裸 Refresh Token 后无条件发给任意地址。
- 每次构造 Cookie Header 校验请求主机、路径、协议、到期与环境；生产 Secure Cookie 不发送到 HTTP。SameSite 是浏览器语义，不把它当作原生主机 / 路径校验的替代。
- Keychain namespace 按 Bundle 标识与规范化 API 环境隔离，包含 scheme / host / port / 基础路径；不让测试和生产共用凭证。
- 前台使用可采用仅本机、解锁后可读的 Keychain 可访问级别；不启用跨设备同步或 Face ID 强制门禁，本版没有后台认证任务。
- 登录 / 刷新成功需校验新 Cookie、串行替换完整快照并等待保存完成；保存失败不得报告“登录完成”或“已恢复”，应阻止业务并提供重新登录 / 清理重试。
- 不在 UserDefaults、普通文件、URLCache、调试日志或崩溃字段中记录密码、完整 Cookie、Token。

Cookie 轮换已在服务端生效而本机保存失败时，不能假定旧 Cookie 仍有效。应进入凭证错误状态，允许清理并重新登录；无法原子完成服务端与本地事务时如实反馈。

## 4. 并发刷新与身份隔离（AUTH-04）

SessionCoordinator 统一执行：

1. 同身份并发业务 401 共享一个 `Task` 刷新；单个页面取消不能取消其他请求仍在等待的共享刷新。
2. 原请求记录发送时 Token 与身份代次。如果当前 Token 已变为新值，使用新 Token 重放一次，不再次刷新。
3. 否则等待共享 refresh，成功后重放一次；同一原请求最多一次认证重放，再次 401 结束并统一处理失效。
4. 登录、注册、重置密码、公共验证码和 refresh 不进入自动刷新。修改密码及其验证码属于受保护操作。
5. 刷新明确 401 才触发一次失效清理；临时网络 / 5xx 传播可重试错误，保留凭证。
6. 登录 / 退出 / 身份失效变更会话代次，所有迟到的 Token、Cookie、查询和错误回写均检查代次。Cookie 的 Keychain 写入检查也必须在串行临界区内。
7. 刷新适配层不再次触发刷新；JSON body 保留为可重用数据。普通传输失败不套用认证重放策略。

身份清理不只是清空 Token：需取消请求、释放业务缓存、关闭 Sheet / 录入页、清空三 Tab 导航。退出后不能通过返回手势看到上一账号流水。

## 5. 验证码与密码（AUTH-05）

| 场景 | purpose | 发送参数 |
| --- | --- | --- |
| 注册 | `register` | email、purpose |
| 忘记密码 | `reset_password` | email、purpose |
| 修改密码 | `change_password` | 仅 purpose，携带 Bearer，邮箱由服务端确定 |

发送成功后显示默认 60 秒冷却，若响应包含 `retryAfterSeconds` 则按服务端值处理。使用截止时间计算剩余秒数，回前台重算，不通过后台暂停 Timer 绕过冷却；切换邮箱不立即解除现有组件冷却。失败可更正当前输入后重试，频控错误要持续展示等待时间。

修改密码成功维持服务端允许的当前会话，不声称“所有设备已退出”。重置 / 修改密码的实际会话状态以后续接口返回为准。

## 6. 退出与清理（AUTH-06）

用户确认退出后进入退出中，暂停新业务提交；协调已在途的 refresh，必要时使用有效 Access Token 调用受保护的 `POST /auth/logout`。退出中不启动额外竞争刷新。

- 服务端确认成功：递增身份代次，取消旧任务，清除内存、当前环境 Cookie / Keychain、缓存与草稿，清栈进入登录。
- logout 明确失败 / 超时：说明“退出未完成，请重试”，不声称服务端会话已撤销；界面可保留当前会话状态，但不得自动跳入新账号。
- 服务端已退出而 Keychain 删除失败：立即阻断旧业务，进入本地清理失败状态并重试删除；不能重启后直接恢复旧身份。
- 明确认证失效：按统一失效流程清理，而不是反复要求已失效 Token 调 logout。

## 7. 验收

AUTH-01–06 均须覆盖正常和失败路径：无 Cookie 冷启动、Keychain 恢复、并发 401、迟到旧 Token、最多一次重放、refresh 503 保留凭证、Cookie 轮换持久化失败、退出中迟到响应、账号切换、Cookie 路径 / Secure / 到期、验证码前导零与回前台冷却。

原生 Keychain 与 URLSession Cookie 行为必须在 iOS 模拟器及至少一台真机验证；测试替身不能替代设备证据。
