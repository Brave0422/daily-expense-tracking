## 要求

1. 一笔支出一定要绑定且只能绑定一个二级分类，不绑定一级分类，通过二级分类来判断它的一级分类归属。标签和事件非必须。
2. 收入只选一级分类
3. 查询数据时，一级分类、二级分类、标签、事件都可以做筛选条件，二级分类的列表取值受一级分类影响
4. 分类分系统默认和用户自定义两种
   - 系统默认分类
     用户无法进行编辑、删除，但可以往系统默认的一级分类中添加自定义的二级分类。用户可以调整一级分类以及二级分类的顺序
   - 自定义分类
     用户可自行添加一级分类、二级分类，包括名称、图标、展示顺序调整。
5. 标签、事件没有默认，用户可创建、编辑、删除
   - 一笔金额可以有多个标签，一个标签也可以被多笔金额使用，即多对多。
   - 一笔金额只能有一个事件，但是一个事件可以有多笔金额。比如2026年9月21日去游乐园玩，除了门票钱，可能在游乐园内购买了零食，回去途中又选择了打车，所以这个事件涉及到了3笔消费：门票、零食、交通出行，所以设定事件为一对多。

## 分类表

category

| 字段          | 类型与要求                                                              | 说明                                       |
| ------------- | ----------------------------------------------------------------------- | ------------------------------------------ |
| id            | INT AUTO_INCREMENT PRIMARY KEY                                          | 主键                                       |
| owner_user_id | INT NULL，FK -> users.id，ON DELETE RESTRICT                            | 所属用户id；为NULL表示系统默认分类         |
| type          | VARCHAR(20) NOT NULL，取值仅限 expense / income                         | 分类所属的金额类型                         |
| parent_id     | INT NULL，FK -> category.id，ON DELETE RESTRICT                         | 父级分类id；一级分类为NULL                 |
| name          | VARCHAR(50) NOT NULL                                                    | 分类名称                                   |
| default_sort  | INT NOT NULL DEFAULT 0，值不得小于0                                     | 未设置用户自定义顺序时使用的默认排序值     |
| level         | TINYINT NOT NULL，取值仅限1或2                                          | 分类层级                                   |
| icon_key      | VARCHAR(100) NULL                                                       | 图标资源标识；系统分类和自定义分类均可使用 |
| archived_time | DATETIME NULL                                                           | 归档时间，NULL表示未归档                   |
| created_time  | DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP                             | 创建时间                                   |
| updated_time  | DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 更新时间                                   |

分类表约束：

1. `level = 1` 时 `parent_id` 必须为NULL；`level = 2` 时 `parent_id` 必须非NULL。
2. `type = income` 时只允许一级分类；支出允许一级、二级分类。
3. 二级分类的父分类必须是一级分类，并且父子分类的 `type` 必须相同。
4. 用户自定义二级分类可以挂在系统一级分类下，也可以挂在该用户自己的一级分类下，但不能挂在其他用户的一级分类下。
5. 同一归属、金额类型和父分类下，未归档的分类名称不能重复。由于MySQL唯一索引对NULL的处理方式，这条规则建议由业务层校验。
6. 分类删除统一采用逻辑归档，即设置 `archived_time`，不进行物理删除；已被金额记录引用的分类归档后仍需保留历史关联。
7. 归档一级分类时，如果它下面还有未归档的二级分类，则拒绝归档。用户必须先归档其下所有二级分类。
8. 建议建立索引 `INDEX(owner_user_id, type, parent_id, archived_time, default_sort)` 和 `INDEX(parent_id)`。

## 用户分类排序表

user_category_sort

| 字段         | 类型与要求                                                              | 说明         |
| ------------ | ----------------------------------------------------------------------- | ------------ |
| category_id  | INT NOT NULL，FK -> category.id，ON DELETE RESTRICT                     | 分类id       |
| user_id      | INT NOT NULL，FK -> users.id，ON DELETE CASCADE                         | 用户id       |
| sort_order   | INT NOT NULL，值不得小于0                                               | 用户分类顺序 |
| updated_time | DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP | 顺序更新时间 |

用户分类排序表约束：

1. 使用 `PRIMARY KEY(user_id, category_id)`，不需要额外的自增id。
2. 建议建立 `INDEX(user_id, sort_order)`。
3. 仅在用户自定义某个同级分类列表的顺序时保存排序记录。首次调整一级分类时，保存同一金额类型下所有可见一级分类的顺序；首次调整二级分类时，只保存同一父分类下所有可见二级分类的顺序。未自定义的列表使用 `default_sort`。
4. 一级分类只能在相同金额类型内排序；二级分类只能在相同父分类下排序。
5. 用户只能为系统分类或者自己的自定义分类设置顺序。
6. 已经自定义排序的范围出现新分类时，新分类先排列在已有用户排序之后，并以 `default_sort, id` 决定多个新分类之间的顺序；用户下次调整时再保存完整顺序。

record_tag

## 金额记录关联要求

金额记录表至少需要以下分类相关字段：

| 字段        | 类型与要求                                          | 说明                               |
| ----------- | --------------------------------------------------- | ---------------------------------- |
| category_id | INT NOT NULL，FK -> category.id，ON DELETE RESTRICT | 支出绑定二级分类，收入绑定一级分类 |
| event_id    | INT NULL，FK -> event.id，ON DELETE RESTRICT        | 可选事件；一笔金额最多一个事件     |

跨表业务约束：

1. 金额记录、用户自定义分类、标签和事件必须属于同一个用户；系统分类可供所有用户使用。
2. 支出记录的 `category_id` 必须指向 `type = expense` 的二级分类。
3. 收入记录的 `category_id` 必须指向 `type = income` 的一级分类。
4. 创建或修改金额记录时，不能选择已经归档的分类、标签或事件；历史记录仍可读取已归档数据。
5. 建议在金额记录表建立 `INDEX(category_id)` 和 `INDEX(event_id)`。

统一身份约束：

1. 下列所有业务方法中的 `userId` 均表示当前登录用户id，由Controller从JWT等登录凭证解析后的认证上下文中取得，再传给Service。
2. `userId` 不作为路径参数、查询参数或请求体字段由客户端提交，避免客户端伪造其他用户id进行越权访问。
3. Service必须使用该 `userId` 查询用户可见分类，并校验分类的所属关系；不能仅依赖客户端传入的分类id。

| 分类排序         | `reorder(userId, dto)`            | `PUT /categories/order`  | 对指定金额类型下的一级分类，或者指定父分类下的二级分类进行批量排序 |
| 创建分类         | `create(userId, dto)`             | `POST /categories`       | 根据 `parentId` 判断创建一级分类还是二级分类                       |

#### 获取用户所有分类

| 字段              | 是否必填 | 说明                                                |
| ----------------- | -------- | --------------------------------------------------- |
| `type`            | 否       | `expense` 或 `income`；不传时返回全部金额类型的分类 |
| `includeArchived` | 否       | 是否包含已归档分类，默认值为 `false`                |

业务要求：

1. 查询结果包含系统默认分类和当前用户创建的分类，不得返回其他用户的自定义分类。
2. 默认不返回已归档分类。
3. 支出分类按一级、二级分类组成树形结构；收入只返回一级分类。
4. 返回结果需要合并 `user_category_sort` 中当前用户的排序；没有用户排序记录时使用 `default_sort, id` 排序。

#### 创建分类

`CreateCategoryDto`：

| 字段       | 是否必填 | 说明                                                       |
| ---------- | -------- | ---------------------------------------------------------- |
| `type`     | 是       | `expense` 或 `income`                                      |
| `name`     | 是       | 分类名称                                                   |
| `iconKey`  | 否       | 图标资源标识                                               |
| `parentId` | 否       | 父级分类id；不传或为NULL时创建一级分类，传值时创建二级分类 |

业务要求：

1. 客户端不传 `level`，由后端根据 `parentId` 推导：`parentId` 为空时为一级分类，不为空时为二级分类。
2. 收入只允许创建一级分类，`type = income` 时不允许传入 `parentId`。
3. 创建二级分类时，父分类必须存在、未归档、属于一级分类，并且父子分类的 `type` 必须相同。
4. 用户自定义二级分类只能挂在系统一级分类或者当前用户自己的一级分类下。
5. 创建的自定义分类必须将 `owner_user_id` 设置为当前用户id，不接受客户端指定所属用户。
6. 创建前需要校验同一归属、金额类型和父分类下是否存在同名的未归档分类。
7. 对外只保留一个 `create` 方法；Service内部可以根据 `parentId` 分别调用一级分类和二级分类的校验逻辑。

#### 编辑分类

`UpdateCategoryDto`：

| 字段      | 是否必填 | 说明                               |
| --------- | -------- | ---------------------------------- |
| `name`    | 否       | 新分类名称                         |
| `iconKey` | 否       | 新图标资源标识；传NULL表示清除图标 |

业务要求：

1. 只允许编辑当前用户自己的未归档分类，系统默认分类和其他用户的分类不可编辑。
2. 普通编辑只允许修改 `name` 和 `icon_key`，不允许修改 `owner_user_id`、`type`、`level` 和 `parent_id`。
3. 修改名称时，需要重新校验同一归属、金额类型和父分类下是否存在同名的未归档分类。
4. 名称和图标通过同一个 `update` 方法进行局部更新，不拆分成“编辑名称”和“编辑图标”两个方法。
5. 如果未来支持将二级分类移动到其他一级分类，应单独设计移动分类的业务方法，不并入普通编辑。

#### 分类排序

`ReorderCategoriesDto`：

| 字段          | 是否必填 | 说明                                                       |
| ------------- | -------- | ---------------------------------------------------------- |
| `type`        | 是       | `expense` 或 `income`                                      |
| `parentId`    | 否       | 不传或为NULL时调整一级分类；传值时调整该父分类下的二级分类 |
| `categoryIds` | 是       | 当前排序范围内全部可见分类id组成的有序数组                 |

业务要求：

1. 调整一级分类时，所有分类必须属于同一个金额类型；调整二级分类时，所有分类必须属于同一个父分类。
2. `categoryIds` 必须覆盖当前排序范围内的全部可见分类，不能缺少、重复或者包含范围外的分类。
3. 用户可以对系统分类和自己的自定义分类排序，但不能为其他用户的分类创建排序记录。
4. 按照 `categoryIds` 的数组顺序批量新增或更新 `user_category_sort.sort_order`。

#### 删除分类

1. 删除接口统一执行逻辑归档，设置 `archived_time`，不物理删除分类记录。
2. 只允许归档当前用户自己的未归档分类；系统默认分类和其他用户的分类不可归档。
3. 归档一级分类前必须检查其下是否存在未归档的二级分类；如果存在则拒绝归档，用户需要先归档全部二级分类。
4. 已被金额记录引用的分类仍可归档，历史金额记录继续保留并能够读取该分类；创建或修改金额记录时不能再选择已归档分类。
