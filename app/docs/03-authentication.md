# 03 账户与认证

[返回主 PRD](../PRD.md) · [API 契约](09-api-contracts.md) · [代码规范](02-flutter-code-standards.md)

## 1. 目标与范围

实现登录、注册、忘记密码、登录态修改密码、验证码、重启后的会话恢复与退出登录。沿用当前后端 Cookie 双 Token 流程，用户已确认该方案；不新增认证端点，也不把 Refresh Token 改为 JSON 请求 / 响应。

## 2. 页面与表单

| 页面 | 输入与操作 | 成功结果 |
| --- | --- | --- |
| 登录 | 邮箱、密码、密码显示切换、注册 / 忘记密码入口 | 保存内存 Access Token，进入流水 |
| 注册 | 邮箱、密码、验证码、发送验证码 | 注册成功后用相同邮箱和密码调用登录 |
| 忘记密码 | 邮箱、新密码、验证码、发送验证码 | 提示重置成功，返回登录，不自动登录 |
| 修改密码 | 新密码、验证码；发送到当前账号注册邮箱 | 提示成功，清空敏感表单并返回我的；维持当前有效会话 |
| 启动恢复 | 恢复中、网络错误、重试 | 恢复成功进入业务页；没有会话进入登录 |

邮箱 trim 后转小写。密码 6–20 位、不 trim；验证码六位数字并保留前导零。输入错误就近显示，服务端错误展示在当前表单，提交时禁止重复点击。

注册已成功但随后登录失败时，应提示“注册成功，请登录”，而不是要求再次注册。普通失败保留当前输入；页面明确退出、成功或会话清理时释放密码和验证码。

## 3. Cookie 与凭证存储

- Dio 配合 CookieManager 和 Cookie Jar 接收 Set-Cookie，后续刷新携带匹配主机 / 路径的 Cookie。
- Cookie Jar 使用自定义 Storage，通过 `flutter_secure_storage` 持久化。不能直接采用普通 FileStorage 保存长期 Refresh Cookie。
- 保留 Cookie 的主机、路径、Secure、HttpOnly、有效期等属性，不只保存一个裸 Token；不忽略 Cookie 过期时间。
- Access Token 只保存在内存中。App 重启后使用安全存储中的 Refresh Cookie 重新获得 Access Token。
- 业务请求使用 Bearer；Refresh Cookie 的服务端 Path 为 `/api/auth`，无需发送给所有业务路径。
- 普通请求客户端和独立刷新客户端共用同一 Cookie Jar。刷新客户端不再触发 401 自动刷新，防止递归。
- 登录 / 刷新成功必须等待新的 Cookie 持久化完成。退出后的旧响应不得重新写入 Token 或 Cookie。
- Cookie 安全存储失败、损坏或写入失败需报告并允许重新登录，不能假装已经建立可恢复会话。

后端生产环境使用 Secure Cookie，所以生产 App 请求必须使用 HTTPS。开发直连时保持现有 `/api/auth` 路径；经过反向代理时专项核对 Cookie Path。

## 4. 会话状态与启动顺序

会话最少包含恢复中、已登录、未登录和恢复暂时失败四类状态。恢复尚未完成时展示启动页，不先闪现登录页或业务页。

1. 初始化平台绑定和安全存储，装载 Cookie，再创建统一网络依赖。
2. 没有可用 Refresh Cookie：进入未登录，不发送无意义的恢复请求。
3. 有 Cookie：调用 `POST /api/auth/refresh`，成功保存内存 Access Token，再开放受保护路由。
4. 刷新返回明确 401：清除当前凭证和旧业务状态，进入登录页。
5. 网络不可用、超时或 5xx：保持恢复暂时失败，保留凭证，显示重试；不把临时故障误判为退出登录。

不依赖当前用户资料接口。我的页面可展示当前登录输入的邮箱；重启恢复后无法取得邮箱时显示“已登录”，不能伪造用户信息或根据未验证数据冒充资料接口。

## 5. 并发 401 与刷新

AUTH-01：同一会话中的并发 401 共享一个 Future 刷新任务，不能每个请求各调用 refresh。

AUTH-02：每个原请求最多在认证恢复后重放一次；再次 401 即结束，不形成循环。

AUTH-03：登录、注册、忘记密码和刷新请求不触发自动刷新。注册 / 忘记密码验证码属于公共请求；修改密码验证码属于受保护请求。

AUTH-04：若失败请求携带旧 Access Token，而当前会话已刷新为新 Token，直接使用新 Token 做一次重放，不再次轮换 Refresh Cookie。

AUTH-05：刷新明确失效后统一执行一次会话清理与跳转；网络 / 服务器暂时失败返回可重试错误，不批量清空凭证。

AUTH-06：以会话序号标识刷新任务。账号切换、退出或清理后，旧任务不能恢复旧身份；CookieManager 的响应持久化也受同一保护。

AUTH-07：请求体重放需要保证可复用。首版使用 JSON 请求；一般超时重试与因认证守卫拒绝而重放严格区分。

## 6. 验证码与密码流程

- purpose 使用 register / reset_password / change_password，参数见 API 文档。
- 发送成功显示提示并启动默认 60 秒冷却；服务端返回 retryAfterSeconds 时尊重服务端值。
- 冷却基于“可再次发送的截止时间”，恢复前台时重新计算，不能因 Timer 暂停而延长或绕过冷却。
- 更换邮箱不绕过该发送组件已有冷却；验证码仍按当前用途校验。
- 重复点击发送、保存和密码提交均受加载锁保护；离开页面释放 Timer。
- 修改密码时不让用户填写另一个邮箱，验证码发送对象由服务端根据会话确定。
- 当前修改密码接口不声明撤销所有会话；App 不擅自实现“全部设备退出”。后续明确收到会话失效时按统一规则处理。

## 7. 退出与账号切换

用户确认退出 → 必要时先刷新 Access Token → 调用受保护 logout → 成功后清空 Cookie、安全存储、内存 Token、所有业务状态和草稿 → 进入登录页。

退出请求明确失败时保留当前会话并提示重试，不能声称已撤销服务端会话。服务器已撤销但本地删除失败时不得继续使用旧内存身份，需展示清理错误并重试本地清理。登录新账号前取消旧请求并隔离旧状态。

## 8. 验收场景

- 首次无 Cookie 不闪现业务页；已有 Cookie 可重启恢复。
- 同时多个业务请求返回 401，只发生一次有效刷新，更新后的 Cookie 已安全落盘。
- 旧请求迟到时使用新 Token 重放，不额外刷新；失败重放最多一次。
- 恢复时断网显示重试，凭证未被误删；明确 401 才清理并转登录。
- 退出 / 更换账号期间，迟到刷新与响应不能重新登录旧账号。
- 注册成功但登录失败不会重复注册；验证码前导零、冷却及用途正确。
- 修改密码成功不伪造服务端会话撤销能力；退出成功后旧 Cookie 不能恢复。
